# Дорожная карта развития проекта автоматизации

Этот документ описывает план развития и отладки системы автоматизации расчетов в ANSYS Mechanical.

## Ключевые ограничения и их влияние

**Важно:** Весь Python-код исполняется непосредственно в среде ANSYS Mechanical, которая использует **IronPython 2.7.4 на .NET 4.0**. Это накладывает существенные технические ограничения, которые влияют на реализацию дорожной карты:

1.  **Совместимость с Python 2.7:** Весь код должен быть написан с учетом синтаксиса и особенностей Python 2.7 (например, `print "..."` вместо `print(...)`, особенности целочисленного деления).
2.  **Ограничения на библиотеки:** Среда IronPython не поддерживает библиотеки, использующие C-расширения. Это означает, что популярные пакеты, такие как `NumPy`, `Pandas`, `scipy` и многие другие, **не могут быть использованы**. Любые сторонние библиотеки должны быть "чистыми" (pure Python).
3.  **Тестирование:** Современные версии `pytest` не поддерживают Python 2.7 и могут иметь несовместимые с IronPython зависимости. В связи с этим, пункт **1.4. Создание базового набора тестов** должен быть адаптирован: вместо `pytest` следует использовать встроенный в Python модуль `unittest`, который гарантированно будет доступен.
4.  **Установка пакетов:** `pip` не интегрирован в эту среду. Любые совместимые (pure Python) библиотеки должны добавляться в проект вручную, путем копирования их исходного кода в папку проекта и подключения через `sys.path`.

Эти ограничения необходимо учитывать на каждом шаге разработки.

## Этап 1: Стабилизация и отладка основного конвейера

**Цель:** Сделать существующий процесс от геометрии до готовой к расчету модели предсказуемым, прозрачным и устойчивым к ошибкам.

### 1.1. Внедрение системы логирования (Logging)
- **1.1.1.** В главном модуле (например, `AnsysAutomation/main.py`) настроить стандартный модуль `logging` для записи событий в файл `automation.log`.
- **1.1.2.** Установить уровень логирования по умолчанию `INFO`.
- **1.1.3.** Добавить `logger.info()` в начало и конец ключевых функций (`apply_mesh_settings`, `define_loads` и т.д.) для отслеживания хода выполнения.
- **1.1.4.** Внутри функций добавить `logger.debug()` для вывода детальной информации (например, "Применяется размер сетки X к телу Y").
- **1.1.5.** Обернуть вызовы API ANSYS в блоки `try...except` и использовать `logger.error()` для записи любых исключений и сбоев, возвращаемых API.

### 1.2. Валидация конфигурационных файлов (JSON)
- **1.2.1.** Создать в коде Python-словарь или отдельный JSON-файл-схему, описывающий обязательную структуру для каждого типа конфигурационного файла.
- **1.2.2.** Написать универсальную функцию `validate_config(data, schema)`, которая рекурсивно проверяет наличие всех ключей и соответствие типов данных.
- **1.2.3.** В начале конвейера, после загрузки всех JSON, последовательно вызывать эту функцию для каждого из них. В случае ошибки — прерывать выполнение с понятным сообщением.

### 1.3. Рефакторинг и модульность
- **1.3.1.** Провести аудит старых скриптов в корне проекта (`ansys_automation_v01.5.py` и др.) и определить всю еще актуальную логику.
- **1.3.2.** Разбить эту логику на атомарные функции и разместить их в соответствующих модулях пакета `AnsysAutomation` (`core`, `managers`, `utils`).
- **1.3.3.** Переписать вынесенные функции с использованием новой системы логирования (1.1) и валидации (1.2).
- **1.3.4.** После успешного переноса и тестирования функционала, удалить старые скрипты, чтобы они не вносили путаницу.

### 1.4. Создание базового набора тестов (с использованием `unittest`)
- **1.4.1.** Создать корневую директорию `tests/`.
- **1.4.2.** Создать файл `requirements.txt` для документации зависимостей (даже если установка ручная).
- **1.4.3.** Создать первый тестовый файл `tests/test_config_loading.py`, используя модуль `unittest`.
- **1.4.4.** Написать класс `TestConfigValidation`, наследуемый от `unittest.TestCase`, и в нем — метод `test_all_configs_are_valid`, который автоматически находит все `.json` файлы, загружает их и проверяет с помощью валидатора из п. 1.2.

## Этап 2: Реализация и отладка автоматизации контактов

**Цель:** Добиться стабильной и корректной автоматической генерации контактных пар.

### 2.1. Анализ и отладка текущего алгоритма
- **2.1.1.** Подготовить минимальный тестовый проект в Ansys с двумя-тремя телами, на котором стабильно воспроизводится ошибка генерации контактов.
- **2.1.2.** Запустить скрипт автоматизации только на этом проекте с уровнем логирования `DEBUG`.
- **2.1.3.** Проанализировать лог-файл, чтобы точно определить, какие команды отправляются в Mechanical, на какой из них происходит сбой и какое сообщение об ошибке возвращается.

### 2.2. Разработка стратегии назначения контактов
- **2.2.1.** Формализовать и записать (прямо в этом `ROADMAP.md` или в отдельном `DESIGN_DOC.md`) правила создания контактов. Пример: "Правило 1: Для тел из `Named Selection` (NS) 'group_A' и тел из NS 'group_B' создать контакт 'Bonded'. Правило 2: Для всех остальных соприкасающихся пар по умолчанию создавать 'Frictionless'".
- **2.2.2.** Создать в `AnsysAutomation/core` модуль `contact_manager.py` с функцией, реализующей эти правила.

### 2.3. Параметризация контактов в JSON
- **2.3.1.** Спроектировать структуру в JSON для описания правил контактов. Пример: `{"contact_rules": [{"from_ns": "group_A", "to_ns": "group_B", "type": "Bonded", "friction_coeff": null}, ...]}`.
- **2.3.2.** Обновить схему валидации (1.2.1), чтобы она знала об этой новой структуре.
- **2.3.3.** Переписать функцию из п. 2.2.2 так, чтобы она читала правила из загруженного JSON и динамически их применяла.

## Этап 3: Реализация базовой постобработки

**Цель:** Автоматизировать сбор ключевых результатов расчета и их сохранение.

### 3.1. Определение перечня результатов для сбора
- **3.1.1.** Составить в `config_files` главный JSON-файл `postprocessing_config.json`, в котором будет перечислен список результатов для сбора. Пример: `{"results_to_probe": [{"type": "Equivalent Stress", "output": "Maximum"}, {"type": "Total Deformation", "output": "Maximum"}]}`.
- **3.1.2.** Валидатор конфигураций (1.2) должен быть расширен для проверки этого файла.

### 3.2. Шаблонизация объектов `Results` в Mechanical
- **3.2.1.** В скрипте настройки анализа написать логику, которая читает `postprocessing_config.json`.
- **3.2.2.** В цикле для каждого элемента из конфига добавлять в дерево `Solution` соответствующий объект результата (например, `Solution.AddEquivalentStress()`).
- **3.2.3.** Каждому созданному объекту присваивать стандартизированное имя, например `auto_probe_eqv_stress_max`.

### 3.3. Реализация скрипта извлечения данных
- **3.3.1.** Создать функцию `extract_results(solution_object)`.
- **3.3.2.** Функция должна сначала вызывать `solution_object.Solve()`.
- **3.3.3.** После успешного решения, функция должна снова прочитать `postprocessing_config.json`, чтобы знать, какие результаты искать.
- **3.3.4.** В цикле обращаться к объектам по их шаблонным именам (`auto_probe_*`), считывать требуемое значение (`.Maximum`, `.Minimum` и т.д.) и складывать в Python-словарь.

### 3.4. Формирование простого отчета
- **3.4.1.** Создать функцию `write_report(results_data, output_path)`.
- **3.4.2.** На данном этапе функция будет сохранять переданный словарь с результатами в файл `results.json` или `results.csv` в директории проекта.
- **3.4.3.** Интегрировать вызов этой функции в самый конец основного конвейера.
